# Account-only durable attempt lane

Local implementation candidate, not deployed, not production migration approval. Existing keyless web/Android routes and unverified guest behavior have not changed. This additive lane does not make those clients globally replay-safe.

`POST /api/attempt-v2` requires a server account session, exact configured HTTPS Origin and JSON request. It ignores body identities. `action: progress` plus `puzzle_id` returns authoritative progress and an HMAC revision; `action: guess` additionally needs `guess`, UUIDv4 `attempt_id` and `expected_revision`. Persist one pending request before send; resend the same payload/key after uncertainty, never invent a replacement key. Native account bearer authentication is not implemented by this cookie-backed route.

Account existence is checked inside the transaction using a locked current user row; this is NOT JWT revocation/session-freshness or real OIDC proof. Existing puzzle and clue rows are share-locked before any receipt access. The same authorized puzzle object is used for revision and gameplay; no second puzzle answer read occurs. Updates/deletes of those locked rows wait until commit. New clue inserts and uncooperative legacy guess writers are not covered by a universal editor/writer protocol.

The lane is disabled without explicit server-only configuration: `ATTEMPT_V2_ORIGIN`, a dedicated 32-byte `ATTEMPT_V2_REVISION_KEY_HEX`, safe epoch `ATTEMPT_V2_REVISION_EPOCH`, and positive numeric `ATTEMPT_V2_MAX_TOTAL`, `ATTEMPT_V2_MAX_OWNER`, `ATTEMPT_V2_MAX_PUZZLE` with puzzle <= owner <= total <= 999999. No auth/session secret is reused, no secret is embedded, and no environment settings have been changed. Actual production key collection/configuration remains a separate secure deployment step. Missing table/config or DB errors fail closed without falling back to keyless mutation.

One transaction takes scope lock, current account/puzzle/clue row authorization, immutable receipt lookup/fingerprint check, persistent count/byte admission lock, canonical actual history/puzzle revision, real gameplay/awards and receipt insert. Body reading has a five-second total budget plus4KiB retention/strict UTF8. JSON response check is8192UTF8 bytes before insert, but PostgreSQL jsonb text may add whitespace, so DB CHECK can still reject atomically; this returns503 with all awards rolled back, not partial success.

The global count query is deliberately serialized and scans receipts under a global admission lock; this is a bounded correctness candidate, not scalable production admission design. It uses bigint and reserves maximum response bytes. No expiry/cleanup is chosen. Known receipts are checked before new-admission limits. Current account auth and puzzle visibility are rechecked for each request; hidden/deleted/malformed puzzles deny replay, rather than disclose a formerly visible answer. Public responses contain only the bounded existing gameplay fields, not raw records.

READ COMMITTED statements are NOT one MVCC snapshot against legacy writers. Progress and HMAC share the same history array and authorized puzzle object, not a global legacy-writer snapshot. The same caveat remains for revision-to-apply races with legacy writers.

The additive SQL is a DRAFT, not part of schema db-push, and has no receipt backfill or deletion/cascade. A fresh synthetic test table is not existing-data or least-privilege migration proof. Both the existing guess-player-key draft and this table must be reviewed/verified on an approved isolated target before exposing this lane. Do not run production DDL from these notes.

Legacy mutation paths do not take the v2 scope lock. HMAC detects prior visible legacy history changes; it cannot make an uncooperative legacy writer atomic with this lane. Do not advertise global exactly-once until every coexisting writer and supported client follows a reviewed transition contract. Existing anonymous identifiers do not prove ownership; no new token may claim legacy guest history merely from its ID. No old user data or installed phone package is replaced here.

At the November8 checkpoint, the precursor exact-source route harness passed8new cases plus its wrapper (9TAP) against owned PostgreSQL/Prisma, importing this actual exported POST handler and Next request/response types with an explicit auth callback fixture. Coverage includes body/identity/Origin/config failures, durable replay/conflict/stale handling, PROGRESS account isolation, successful commit with HTTP response loss, and pause-controlled existing-row edit/hide races. Earlier separate component checks cover wrong/correct HTTP-response loss and production gameplay atomicity. The checked-in test path/loader/owned-target guard adaptations are source-reviewed, not separately executed. None of this establishes a built Next server or middleware, auth cryptography/provider login, deleted-account replay/delete-lock, new-clue insert/legacy-writer discipline, existing-data migration, durable web/Android pending clients or native runtime. Those remain qualification work. No release or deployment clearance yet.
